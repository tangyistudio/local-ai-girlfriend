# 播放片段而不露出接縫

你有一個所有片段首尾都落在同一張畫面上的片庫（`05-assets.zh-TW.md`），還有一串逐句抵達的、算好的說話片（`04-latency.zh-TW.md`）。這一份講的是怎麼播它們，讓角色看起來永遠不會出錯。

這比看起來難，而困難集中在一個地方：**每一個視覺缺陷都發生在交接的那一刻。** 減少交接次數，就同時減少了所有類別的問題。

---

## 雙緩衝，以及為什麼一個元素不夠

兩個 video 元素疊在一起。一個在前景播放，另一個預載下一支片。前景那個播完時，背景那個接手，兩者互換角色。

單一元素換 `src` 時會露出一張空白畫面，因為新的來源還在載。用一個元素沒有辦法繞過這件事。

## 統治一切的那條規則

**絕不為了一張你還沒有的畫面，去藏起一張你已經有的畫面。**

幾乎每一次「閃黑」都可以歸結為：在新元素真的畫出東西之前就把舊元素藏起來。那時兩層都是透明的，觀眾看到的是頁面背景。

**舊的那一幀是一個完全可以拿來顯示的東西。** 它是樞紐幀——角色坐著不動。多留它 200 毫秒是看不出來的。**露出黑色 16 毫秒則看得出來。**

所以隱藏的條件必須是**「新元素已經呈現了一幀」**，永遠不是一個計時器。

## 閃黑的五個成因，誠實分級

我們花了好幾天一個一個修。它們是獨立的——修好四個之後仍然看得到閃黑。

| | 成因 | 證據 |
|---|---|---|
| 1 | **`moov` atom 在檔案結尾。** 瀏覽器必須把整支片下載完才畫得出第一幀。 | 實測：1.29 MB 的片花了 1.17 秒，1.42 MB 的花了 **1.71 秒**，而保險逾時只有 1,200 毫秒。在編碼端用 faststart 根治；把逾時拉到 3,000 毫秒當第二道防線。 |
| 2 | **預載蓋掉了正在交棒的元素。** 預載器從一個還沒提交的狀態算出「背景元素」，於是換掉了那個即將成為前景的元素的來源。 | 症狀可重現；沒有數值量測。修法：明確追蹤交棒目標，永遠不預載進去。 |
| 3 | **`loadeddata` 不代表已經畫出來。** 它的意思是當前位置的資料已解碼，不是一幀已經抵達合成器。 | ⚠️ **從來沒有被驗證過，我們沒有，別人也沒有。** 我們的工具不合成畫面，所以回報幀呈現的那個 API 從來沒觸發，量到的數字是廢的。這個修法是推理出來的、上線了，並且留下一個「需要實機確認」的待辦——而我們找不到任何它真的發生過的紀錄。已套用的修法：`requestVideoFrameCallback`。 |
| 4 | **硬切路徑沒有設 z-index。** 交叉淡化為 0 時，把新元素設成不透明並不會蓋住在它上面的舊元素；接著舊的變透明，於是有一幀兩者都不可見。 | 決定性的，可以直接從程式碼讀出來。只在交叉淡化因為其他理由被設成 0 之後才浮現。 |
| 5 | **用計時器隱藏舊元素。** 如果「等一幀」的保險逾時先觸發，淡化就在沒有東西可以淡進去的情況下開始了。 | 修法：讓淡化以幀呈現為前提。⚠️ **這一項後來被部分推翻**——見下文。 |

### 成因 5 修過頭了，而那件事值得知道

成因 5 的修法是讓交叉淡化本身去等一幀被呈現。但呼叫端**早就已經等過了**。兩次等待疊加：400 毫秒 + 400 毫秒 + 140 毫秒，而我們量到 **997 毫秒兩層同時可見**。使用者回報「片段一直疊在一起」，那跟我們一開始要解決的抱怨正好相反。

**最終形狀：呼叫端以幀呈現為前提，淡化本身是一個單純的計時器。** 一道閘門，不是兩道。

如果你從這張表只帶走一件事，帶走這個：***「等那一幀」是對的，而把它套在兩個地方是另一個 bug。***

## 硬切還是淡化：取決於片段，而且量得出來

同一個播放器裡有兩個答案，兩個都對。

**片庫裡的片段：硬切，不淡化。** 它們的首尾幀在樞紐幀的 4.6/255 之內，所以那個接點是兩張幾乎一模一樣的畫面。24 fps 下 120 毫秒的淡化會疊合三幀，其中舊片正在動作中（手在放下、眼睛可能正在眨）而新片在靜止。那讀起來就是鬼影，以及前一個動作被切掉。3 次獨立的使用者回報，全部靠移除淡化解決。

**說話片：200 毫秒淡化，必要。** 對嘴片的長度由音訊決定，所以它結束在來源片的任意一幀上。實測來源片中段對樞紐幀的飄移：最大 **16.75**——只有開頭 9 幀與結尾 6 幀在 5 以內。從一個差那麼多的幀硬切到樞紐幀，正是「動作還沒做完就被切掉」那個抱怨。

規則是：**兩邊都由結構保證對齊時硬切，其中一邊可以落在任何位置時淡化。**

### 用對的方式做交叉淡化，否則它比不淡化更糟

直覺的實作是舊的淡出、新的淡入。在深色背景上，中間點兩者都是半透明，合成結果是 `0.5×新 + 0.5×(0.5×舊)`——畫面會**變暗**。兩張一模一樣的畫面反而疊出一個看得見的凹陷。

正確做法：**舊元素維持完全不透明，新元素疊在它上面淡入。** 合成是 `α×新 + (1−α)×舊`，一個真正的交叉溶接。兩張相同的畫面全程保持相同。淡化完成之後才把舊的藏起來。

## 交接是風險的單位：讓它變少

上面每一個缺陷都發生在交接時。所以槓桿最大的改動不是修好交接，是**不要有交接**。

**原地重播同一支片是一次零成本的交接。** 如果下一支片就是正在播的那一支，在同一個元素上設 `currentTime = 0`。不換來源、不等畫面、不做交叉淡化——整條管線被跳過，連同上表裡的每一個失效模式。這件事之所以可行，正是因為樞紐幀不變條件讓循環點是無縫的。

圍繞這一點建立待機輪替，把一個約 30 秒的循環裡的交接次數從大約 5 次降到 2 次，也就把上述所有問題的曝險降低了差不多同樣的倍數。

⚠️ **原地重播只對真正靜止的片有效。** 我們先拿動作片試過，角色連續重複同一個手勢好幾次——**明顯比我們想避免的切換還糟**。這件事依賴 `05-assets.zh-TW.md` 裡的位移量測。

## 另外兩個，各會花掉你一天

**`requestAnimationFrame` 在頁面沒有被合成時不會觸發。** 背景分頁、被遮住的視窗、切換到別的 App 的手機。如果你用 rAF 當轉場的起點，新元素會永遠停在 opacity 0、舊的停在 1，而使用者切回來看到的是一張凍住的畫面，同時背景那個元素正開心地播著。實際觀察到：前景停在 3.88 秒且暫停，背景元素的 `currentTime` 還在前進。**改成強制同步 reflow。**

**檢查是哪一個元素發出的事件。** 兩個 video 元素都掛著 `ended` 處理器時，背景元素發出 `ended` 會在前景播到一半時觸發交接，把它的動作切掉。這個 bug 潛伏了好幾週，然後在我們讓舊元素多留 400-540 毫秒的那一天變成常態——**一個 bug 的修法，把一個罕見的競態變成了常態。** 拿事件來源去比對「現在真正該播的是什麼」，用內容比對，不要用一個可能還沒提交的狀態變數。

## 保險

修好上面那些成因、仍然收到回報之後，我們停止再追下一個，改成讓那個失敗不可能發生：**在兩個 video 元素後面墊一張樞紐幀的靜止圖。**

如果兩層真的同時空白，露出來的是角色坐著不動——那跟一張正常的畫面無法區分，因為它就是一張正常的畫面。

⚠️ **這是保險，不是修法。** 如果你還是看到閃黑，那就還有一個轉場要找。但它在你找的期間，把一個看得見的缺陷變成看不見的。

⚠️ 一個細節：**在第一幀影片畫出來之前不要掛上它。** 我們的開場片是從黑畫面淡入的，而一張從一開始就存在的底圖會讓整段變成「角色坐在那裡 → 切成黑 → 再淡進來」，比它本來要防的那個閃黑更糟。

## 實作

這一份描述的是做法；`player/` 是它的實作。與框架無關、零依賴、不附框架包裝；這個類別與框架無關。`player/examples/demo.html` 拿隨附的生成片庫把它跑起來。

⚠️ 這份清單裡有兩個缺陷是**靠跑那個 demo 發現的**，不是靠讀程式碼——而且兩個在被抽取的那個上線元件裡都存在。一支在交棒進行中載入失敗的片段會讓播放器永久凍結；而它的恢復又會再挑同一支壞片段，因為「不可載入」的過濾只套用在輪替池上、沒有套用在佇列上。**單元測試從頭到尾都是綠的。**

該做對的部分，依「發現它們的代價」排序：

1. 只在新的那一幀已經畫出來時，才隱藏舊的那一幀。**一道閘門。**
2. 對齊的片段硬切；只有在其中一邊可以結束在任何位置時才淡化。
3. 淡化的做法是讓舊的維持不透明，不是兩邊一起淡。
4. 下一支片就是當前這一支時，跳過整個交接。
5. 對 `ended` 採取行動之前先驗證事件來源。
6. 在所有東西後面墊一張靜止畫面當保險。

## 黑閃，以及為什麼讀程式碼找不到它

有人回報播放器在片段之間會閃黑。片子本身不是原因——逐幀掃過，每個檔案裡最暗的一幀
都在該檔平均值的 97% 以上，相鄰幀之間最大的降幅是 0.8（滿分 255）。從來沒有暗的東西被編碼進去。

找到它的方法是**逐個動畫幀取樣合成後的頁面**：每一幀去看最上層是哪個元素、它是不是不透明、
它有沒有東西可以畫。一次 45 秒的取樣就抓出兩個缺陷。

**3 幀最上層元素的 readyState 是 0 或 1。** 沒有解碼幀的 video 元素是透明的、不是黑的，
所以播放器露出了自己的背景色。那就是那個閃。

**46 幀——770 ms——畫面凍在第一幀**，而下面那支即將退場的片，聲音還在跑。
超過半秒的「有聲音、嘴對不上」，每一次答覆的開頭都會發生。

兩者根因相同，而且出問題的那個檔案裡，就寫著它自己違反的那條規則。
`requestVideoFrameCallback` 只對**正在被合成**的元素觸發。交接時它被呼叫在即將被推上前景的
那個元素上——那個元素是暫停的、opacity 是 0、因此沒有被合成。它永遠不可能觸發。
每一次交接都掉到 400 ms 的保底逾時，然後不管有沒有畫面都把元素推上去。

把 `play()` 移到等待之前有幫助但沒有修好：opacity 0 的元素依然不被合成，
回呼依然不觸發，還剩 18 幀的凍結畫面。

正解是不要等，並且把順序反過來：

    硬切：  先把新的推到最上層，舊的完全不透明地留在它下面 -> play()
            -> 等到真的有一幀被畫出來，才把舊的藏起來

    溶接：  play() 和溶接在同一個 tick 開始；溶接本來就會讓舊的
            在整段期間保持不透明

兩者都直接來自 `handover.js` 開頭那條規則——寫下來了，然後沒有被遵守：
**絕不為了一個你沒有的畫面，藏掉一個你有的畫面。** 把還畫不出東西的元素推上前景是免費的，
因為它是透明的，透出來的正是前一支片的樞紐幀。

⚠️ 教訓不是「要檢查 readyState」。教訓是：**一個可能靜默地永遠不觸發的等待，
比完全不等更糟**——它在審閱時看起來像防護，在正式環境裡的行為卻是一個固定延遲。
這一段被讀過好幾次，讀的人還剛寫完解釋它的註解。
