# 挑選模型

三個位置——語言、語音、對嘴——和一大堆候選。這一份與其說是推薦，不如說是方法，因為你讀到這裡的時候具體的模型早就換過了，而評估它們的方式不會。

推薦背後的數字在 `00-hardware.zh-TW.md`（顯存）與 `04-latency.zh-TW.md`（速度）。每一個的授權立場在 `07-licenses.zh-TW.md`，而那不是註腳——**它直接淘汰了最熱門的那個對嘴模型的所有商業用途。**

---

## 那個抓得到別人都漏掉的失敗的指標

從這裡開始，因為沒有它，你其餘的評估可以錯得非常有自信。

對嘴品質通常用銳利度與時間抖動來量。兩者都容易計算、都看起來很科學，而且**兩者都會被一條已經安靜地完全停止做對嘴的管線優化到最好**。一支人坐著不動、嘴巴閉著的影片，銳利度完美、抖動為零。

來源專案記錄了 **3 次**「只信指標、沒看畫面」的教訓；其中一次正是這個失敗，另外兩次是縮放錯位與幀數錯配。不同的 bug，同一個根。

**這道檢查：把嘴部區域的動作量拿去跟來源片比。** 來源是一個全程閉嘴的人。如果你的產出的嘴部動作量沒有明顯高於來源，**對嘴就是沒有發生**——不管其他數字看起來多好。

```
motion(output) / motion(source)  <= 1.0   →  對嘴沒有生效
```

**你加的每一個品質指標，都應該配一個在功能停止運作時會「下降」的指標。** 銳利度與抖動兩個都會上升。

## 有意義的比較

四條規則，每一條都是先得到錯誤答案才學到的：

**同一段音訊、同樣的幀數範圍。** 在不同幀數上算出來的數字不可比，而這個差異很容易漏掉，因為兩次執行都成功。這造成過兩次獨立的錯誤結論。

**每一個品質數字都要配一次看畫面。** 我們產出過指標改善而產品變糟的結果——下顎輪廓的指標改善了 11-19%、臉頰的改善了 26%，而人說嘴型「看起來很奇怪」，因為那些指標量的是變化的**量**，抱怨的是**形狀**。

**但不要拿眼睛當篩選器。** 目視審查 39 張縮圖漏掉了 2 支、誤判了 1 支。正確的分工是**指標篩、目視判**：指標挑出值得看的那幾支，人在那幾支上做決定。

**在相信一個工具之前，拿已知答案驗它到底在量什麼。** 更多細節在 `05-assets.zh-TW.md`，那裡有一個量測工具做了四個版本，因為前三個都很有自信地在量錯的東西。

## 對嘴

真正要緊的決定是**即時率**，不是視覺品質。

| | 即時率 | 後果 |
|---|---|---|
| 低於 1.0 | 生成跑得比播放快 | 角色可以連續說話；你可以在當前這句播放時算下一句 |
| 高於 1.0 | 播放跑得比生成快 | 再多管線化也沒用；每一句都是一次等待 |

我們量到一個擴散模型是 **5.08 倍即時**，一個 wav2lip 這一類的管線是 **0.37 倍**——13.3 倍的差距，而且它的嘴還**更清楚**（58% 對 34%）、抖動略低。「比較慢、比較新的模型一定看起來比較好」這個直覺沒有從量測中存活。

**候選，以及通常做決定的那個授權立場：**

| | 速度 | 授權立場 |
|---|---|---|
| wav2lip 這一類 | 量到最快，部署起來約 2.4 GB | **權重禁止商用** |
| Ditto | 這裡沒有做基準測試 | Apache-2.0，含權重 |
| MuseTalk | 這裡沒有做基準測試 | MIT，但拉進了我們沒稽核的元件 |
| LatentSync | 量到 5.08 倍即時 | 程式碼 Apache-2.0，權重 openrail++ |

⚠️ 我們只對其中第一個與最後一個做了基準測試。**Ditto 是我們基於授權理由推薦、卻沒有做基準測試的那一個**，意思是這個 repo 裡的速度數字不是它的數字。如果你走乾淨的商用路線，拿 `bench/` 對它重跑一次。

## 語音

有兩件事決定這個，而且都不是模型卡上的那個指標。

**量短句的牆鐘時間，不要量 RTF。** 即時率是生成時間除以音訊長度，所以一個講得慢的模型會拿到比較好的 RTF，而使用者等得比較久。我們量到一個 RTF 比較好的引擎（1.11 對 1.89），對同樣 10 個字**在時鐘上慢了 32%**，因為它把那些字拉成 3.56 秒而不是 1.36 秒。

**確認你量的是模型還是你自己的設定。** 一個被我們以「太慢、不能即時」淘汰的引擎——每句 11-16 秒——在我們停止每次呼叫都重新編碼參考音訊之後，變成 2.7-3.4 秒。**模型從來不是問題。**

聲音克隆還有一個很容易太晚才發現的約束：**不要做「退回另一種聲音」的降級路徑。** 如果克隆聲音服務掛了，讓請求失敗才是對的。退回到一個內建聲音，會讓同一個角色出現兩種聲音，那比一個錯誤更糟——它破壞了你當初做克隆的目的。**要大聲地失敗。**

## 語言模型

能撐住一個人設的最小的那個。在一張 24 GB 的卡上我們量到：

| | 吞吐量 | 顯存 @ 4k ctx |
|---|---|---|
| 8B | **86.3 tok/s** | 5.11 GiB |
| 27B | **19.9 tok/s** | 約 11.5 GB |

大的那個**每個 token 慢 4.3 倍**。對一個對話型伴侶來說，那是「上一句還沒讀完下一句就到了」與「你要坐在那裡等」的差別。

兩個比參數量更要緊的規格註記：

**上下文才是真正的成本。** 從 4k 預設拉到 32k，8B 模型的佔用**增加 87%**（多 4.4 GB）。伴侶需要人設加歷史，所以要編列上下文的預算，不只是模型的。

**磁碟上的權重低估常駐顯存幾個百分點、低估載入峰值更多**（8B 是 +2.3% 與 +13%），加上上下文之後低估得更多。

## 每個元件該跑在哪裡

這些元件值得留在本機的程度不一樣：

| | 留在本機是因為 | 或者搬走是因為 |
|---|---|---|
| **對嘴** | 它顯存便宜（約 2.4 GB），而且沒有好的託管版本 | - |
| **語音** | 克隆的聲音是你產品的身分 | 它是非 LLM 元件裡最貴的，約 5.1 GB |
| **語言** | 對話永遠不離開這台機器 | 它最容易換成 API，而且是單一最大的節省 |

8 GB 那一格正是這張表的應用：把兩個便宜的留在本機，把貴的放到 API 後面。見 `01-tiers.zh-TW.md`。

⚠️ 那個交換有一個不以 GB 計價的代價。**如果本機推論正是你自架的理由，把語言模型搬到 API 就等於放棄了你當初要蓋的東西。**
