# 為什麼這是好幾個行程而不是一支程式

直覺的設計是一支 Python 程式，載入語言模型、語音模型與對嘴模型，依序呼叫。沒有人這樣蓋，而理由不是架構品味。

**你沒辦法把這些模型裝在同一個環境裡。** 這是其他一切都由此推導出來的約束。

---

## 那個約束

不同的模型釘住同一批函式庫的不同版本，而那些釘法互不相容：

| 元件 | torch | numpy |
|---|---|---|
| MuseTalk | 2.0.1 | 1.23.5 |
| LatentSync | 2.5.1 | 1.26.4 |

那不是兩個你可以折衷的偏好。那是兩個環境，而把它們放進同一個裡面不是「要小心處理」的事，是「做不到」的事。

所以每個模型有自己的虛擬環境，而虛擬環境意味著行程，需要互相溝通的行程意味著協定。localhost 上的 HTTP 是常見答案，而一旦走到這裡，「架構」就只是：**一個模型一個小 HTTP 服務，加上一個依序呼叫它們的協調者。**

你不是在選微服務。是依賴解析替你選了。

## 這件事造成的失敗，而且它是無聲的

共用環境通常不會用 import error 宣告自己。它會安靜地給你錯的建置版本。

把某個套件裝進一個已經有可用 CUDA torch 的環境，會把它換掉，因為那個套件的 `pyproject.toml` 釘了 torch 版本：CUDA 版被反安裝，換上一個 **CPU 版**。什麼都沒失敗。所有東西都 import 成功。`torch.cuda.is_available()` 回傳 `False`，而模型跑在 CPU 上，速度慢到在 benchmark 裡會被淘汰——**以「這是個爛模型」的名義被淘汰，而不是「這是個裝壞的環境」。**

由此得到兩件事：

**安裝順序很重要。** 先裝套件，最後才裝 CUDA torch 建置版，這樣就沒有東西能把 CUDA 版從你腳下抽走。

**重新安裝可能什麼都沒做。** pip 認為 `2.8.0+cpu` 與 `2.8.0+cu126` 是同一版，因為本地版本標籤不參與比對。重裝看起來成功，實際上什麼都沒換。你需要 `--force-reinstall`。

**每次動過環境都要檢查 `torch.cuda.is_available()`**，而且把 `False` 當成壞掉的安裝、不是當成一個結果。**一個在 CPU 上量到的模型不是一個慢的模型，它根本不是一次量測。**

## 這樣做換到什麼

被迫分離的結果，在依賴之外還有好處：

**你可以逐元件量測。** Windows 上沒有 per-process 顯存（見 `00-hardware.zh-TW.md`），所以歸屬記憶體的唯一方法是啟停元件、取差值。那之所以可行，正是因為每個模型都是一個你停得掉的行程。在單一程式的設計裡，你根本沒辦法問「TTS 花多少」。

**你可以把某一個元件搬到別的地方。** 8 GB 那一格之所以成立，正是因為語言模型可以是一次 API 呼叫而不是本機行程，其他什麼都不用改。如果它是一個 import，就不可能。

**一個模型崩潰不會把其他的一起帶走。** 這些是研究等級的程式庫，它們真的會崩。

## 這樣做的代價

**每個行程各付一次的 GPU 開銷。** 一個 CUDA context、一份框架執行期、以及一個保留已釋放區塊而不歸還的配置器。這是為什麼我們部署起來的對嘴服務量到 2.4 GB，而廣為流傳的模型數字是 1.3 GB 的一大部分原因。兩個模型兩個行程，這筆要付兩次。

**每一跳都要序列化。** 音訊與影片在行程之間以檔案或 HTTP body 傳遞，不是以已經在 GPU 上的張量傳遞。對這個工作負載而言它不是瓶頸——語音合成以一個數量級輾壓它，見 `04-latency.zh-TW.md`——但它也不是免費的。

**沒有共用的 GPU 排程器。** 每個行程各自向驅動要記憶體，沒有東西協調它們。那是 `08-ops.zh-TW.md` 裡**顯存爭用**那幾個故障的成因——被餓死的服務，以及長到 38 個行程的看門狗。那裡其他的故障成因不同。

## 因此長出來的形狀

```
     browser  ──HTTP──►  orchestrator  ──┬──►  LLM service      (own env)
                                          ├──►  TTS service      (own env)
                                          └──►  lip-sync service (own env)
```

協調者不持有任何模型。它把回覆切成句子，逐句呼叫 TTS 再呼叫對嘴，並在每一段完成時就串回去。**那個逐句管線化才是讓等待可以忍受的東西**，寫在 `04-latency.zh-TW.md`。

### 這個形狀需要一件我們的實作沒有的東西

對嘴服務必須能接受**不是它自己產生的音訊**。

我們量的那個實作做不到：它把語音寫進暫存目錄，每一次快取未命中都呼叫 TTS 服務，**沒有任何端點接收現成的音檔**。在你想把 TTS 跑到別的地方之前，這都沒問題——而「別的地方」正是 8 GB 那個配置。

如果你要蓋這個，**從一開始就給對嘴服務兩個入口**：一個吃文字並負責協調，一個吃音訊而且只做對嘴。第二個才是讓各等級可以重新配置的關鍵。

## GPU 住在哪裡

上面沒有任何一件事要求模型行程與網頁前端在同一台機器上，而實務上它們不在：前端在一台永遠開著的主機上，模型行程在有 GPU 的那台機器上，透過隧道連過去。

⚠️ 這個切分有一個值得為它做設計的性質：**GPU 那台掛掉時，前端還活著**。網站照樣回 200，而讓它有用的那個東西已經死了，沒有任何人被通知。不管你蓋什麼，**從外部健康檢查 GPU 服務並對那個告警，不要對網頁層告警**——見 `08-ops.zh-TW.md`。
