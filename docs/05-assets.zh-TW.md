# 片段：一個架構，以及怎麼判斷你的片段壞了

回覆在算的時候，角色必須在畫面上做一件看起來合理的事。那意味著一個短片段的片庫，以及一套在它們之間切換而看不出接縫的方法。

播放機制在 `06-playback.zh-TW.md`。這一份講的是片段本身：讓無縫切換成為可能的那個不變條件，以及告訴你某支片違反了它的量測工具——因為我們有好幾支片違反了，而且是無聲地違反，**而我們為了抓它做的前三個工具都在量錯的東西**。

---

## 不變條件：每一支片的首幀與尾幀都是同一張畫面

用同一張靜止圖當每一支片的首幀與尾幀去生成。叫它樞紐幀。

```
                    ┌──────────┐
         ┌─────────►│  pivot   │◄─────────┐
         │          │  frame   │          │
    ┌────┴────┐     └────┬─────┘     ┌────┴────┐
    │ listen  │          │           │  nod    │
    └─────────┘     ┌────┴─────┐     └─────────┘
                    │  think   │
                    └──────────┘
```

因為每一支片都以同一個姿勢開始與結束，**任何一支片可以接任何一支片**，而它們之間的切點在沒有任何交叉淡化的情況下是看不見的。那個接縫是兩張一模一樣的畫面。

這比聽起來值錢。另一條路——在結束姿勢不同的片段之間做交叉淡化——會在臉上產生看得見的鬼影，而且**你沒辦法用淡化解決一隻手在不同位置的問題**。

**實測：** 在**一個** 65 支反應片的池子裡，任何一支的首幀或尾幀對樞紐幀的最大偏離是 **255 分之 4.6**——約 1.8%，而那個池子裡沒有嚴重偏離的。

⚠️ 那是某一個時間點的某一個池子，不是這個架構的性質。**其他片段確實違反過這個不變條件**——一支講話底片量到 8.64、門檻是 9，而人一眼就看出來（見下面「門檻要對著眼睛校準」）。這個不變條件成立是因為它**被檢查**，不是因為生成器會遵守它。

在那個對齊程度下，硬切是真的看不出來的，而 120 毫秒的交叉淡化嚴格來說更糟：它把兩個不同時刻的嘴與眼睛疊在一起。

### 這個不變條件的代價

**你只能在片段邊界切換。** 如果使用者在一支 10 秒的待機片播放時送出訊息，他要等那支片播完，角色才能反應。

所以片長不是一個數字。它依「有沒有東西在等」而分層：

| 片段類型 | 播放時機 | 長度 |
|---|---|---|
| 待機 | 沒有東西在等 | 可以長 |
| 聆聽／思考 | 使用者在等回覆 | **必須短** |

這件事做錯的話分層就白做了：如果你是在回覆**開始算之後**才切到短片段，使用者早就已經在等一支長待機片了。**在任何「回覆即將到來」的跡象出現的當下就切到短片池——第一次按鍵，不是送出。**

## 構圖決定你需要多少 GPU

這是把素材工作連回硬體預算的那個發現，而且我們沒有預期到。

一個被廣為分享的低顯存建置，對嘴跑在 256x256。作者說那個糊「基本上看不出來」。**那是真的——對他的構圖而言。** 角色只佔畫面的一側、被側光打亮、場景偏暗。

我們的是正面、明亮、大特寫：每一個讓對嘴瑕疵最大化可見的條件。

**同一類模型、同樣的解析度、不同的結論。** 我們之中一個可以出貨那個對嘴品質，另一個不行。

⚠️ 顯存數字也不是同一個：他們發表的是 1.3 GB，我們部署起來的行程量到 2.4 GB，而 `00-hardware.zh-TW.md` 用很長的篇幅論證那兩者不是同一個量。**這裡講的是鏡頭，不是預算。**

所以「我需要多大的卡」有一部分是美術指導的問題。**在你為了修畫質問題去買硬體之前，先確認你的鏡頭有沒有在幫你。** 側光與暗場景是免費的；顯存不是。

## 量你的片段

四個工具，各自抓到其他工具抓不到的東西。四個都跑；它們的不一致很有用。

### 1. 這支片有回到樞紐幀嗎？

把首幀與尾幀**拿去跟樞紐圖比**，不是拿它們互比。

⚠️ 這個區別很要緊而且很容易搞錯。一支首尾幀**彼此**吻合、但整體偏離樞紐幀的片，在自我比較裡會通過，而它跟其他每一支片接起來仍然會跳。**要跟樞紐幀比。**

### 2. 接縫看不看得見？除以這支片動多少

這是這裡最能推廣的想法，而且它反直覺。

原始的接縫誤差沒有預測力。在兩批片上量到：

| | 首尾誤差 | 相鄰幀動作量 | 比值 | 看得見嗎 |
|---|---|---|---|---|
| A 批 | 2.5 - 2.7 | 0.33 - 0.53 | **4.9 - 7.7** | 會跳 |
| B 批 | 2.4 - 2.6 | 2.4 - 4.6 | **0.55 - 1.2** | 無縫 |

**兩批的接縫誤差是一樣的。** 大約 2.5，那是編碼雜訊而不是姿勢誤差。不同的是分母：A 批幾乎不動，所以同樣的誤差相對於它正常的逐幀變化被放大 5-7 倍，眼睛就挑得出來。B 批夠活潑，接縫落在雜訊裡。

```
可見度 ≈ 接縫誤差 ÷ 相鄰幀差異的中位數
```

一支很靜的片需要比一支活潑的片緊得多的循環。裁切救不了——我們試過，工具回報現有的尾幀已經是最佳解。

### 3. 這支片真的是靜的嗎？

不要從檔名推論。我們有一組命名為待機、並當成「休息」層在用的片，量了角色本身的位移：

| | 位移 |
|---|---|
| 一支舊片 | **6.34** |
| 重生的「待機」片 | **20 - 39** |

重生的那組動得**多 3-6 倍**。它們是為了修正「角色太靜」這個抱怨而重生的，而修過頭了：每一支都變成「大動作、彈回原點」，因為樞紐幀不變條件保證了那個回歸。**整個池子裡沒有任何一支能當休息用。**

回報的症狀是「它一直在動，沒有停下來」，而**三次不同的、透過修改播放規則來解決的嘗試全部失敗**，因為問題在素材裡。**量位移，不要從名字推論它。**

### 4. 該閉著的時候嘴是開的嗎？

片段的規格是全程閉嘴——對嘴是後製上去的。生成器不總是遵守，而結果是一個看起來在講話但沒有聲音的角色。

**我們為此做了四個偵測器。前三個是錯的。**

| | 偵測器 | 為什麼失敗 |
|---|---|---|
| 1 | 嘴部框內的逐幀像素差 | 分不出「嘴張開」與「頭轉過去」。一支有明顯 o 形開口的片被排到**第 19 名**。 |
| 2 | 嘴部框內最暗的 3% 像素 | 抓到的是飄進框裡的頭髮。一支閉嘴的片量到比它張嘴的版本**更暗**。 |
| 3 | 內唇間距 ÷ 臉高 | 把**露齒微笑**算成張嘴。兩支人一眼就分得出來的片量到 0.1535 與 0.0906。 |
| **4** | **MediaPipe 的 `jawOpen` blendshape** | ✅ 有效，因為同一個模型另外提供 `mouthSmile`——**笑與張下巴在模型裡本來就是兩個維度，不是一個。** |

對著人已經判定過的片做回歸校準，兩群乾淨地分開：

```
目視判「張開」                  目視判「閉著」
0.615                          0.259（同幀笑 0.932）
0.477                          0.230
0.437                          0.154
0.375                          0.003
```

**0.259 與 0.375** 之間有一個乾淨的斷層，所以門檻取 **0.32**，0.24-0.32 標記給人複查。

**解釋前三個為什麼全滅的那一列**，就是 jawOpen 0.259 而 mouthSmile 0.932 的那一支：一個下巴幾乎閉著的大大笑容。每一個基於像素與幾何的偵測器都把它判成張嘴。

⚠️ 這些數字是對一個角色、一種構圖做的回歸。**兩者任一改變就要重新校準。**

⚠️ 驗證方式是掃過一個池子並與人工判定比對：結果完全一致，標記出來的是同樣那幾支，而且最後一支不及格的（0.379）與第一支乾淨的（0.223）之間有乾淨的間隔。

## 門檻要對著眼睛校準，不是對著整數

有一支片以 8.64 通過了門檻 9，而人一眼就看出問題。那個門檻不是從任何東西推導出來的——它是一個方便的整數。

那支片重生到 4.45，抱怨就消失了。**一個從未對人的判斷驗證過的門檻，就是一個你編出來的數字。** 把它設在兩群真的分開的地方，就像上面 jawOpen 門檻的設法。

## 生成片段：兩個陷阱

**蘊含張嘴的詞會讓嘴張開**，即使你已經明確要求閉嘴。`brightly`、`beaming`、`grin`、`laugh`、`surprise` 都帶著它。我們最乾淨的變因分離是：

```
"points at you brightly"                          → 0.525
同上 + 閉嘴指令附在後面                            → 0.546   （沒有比較好）
拿掉 "brightly" + 指令前置                         → 0.001
```

拿掉那個詞有效；在它後面加指令沒有。位置也重要：同一個指令放在動作句**之前**得到 0.202，放在**之後**得到 0.507。

⚠️ 不要直接點名下巴。寫「Her jaw stays closed」讓它**更糟**——從 0.477 變成 0.642。

**但種子的變異比提示詞大，而我們一開始把這件事講得太肯定。** 兩支提示詞幾乎相同的片得到 0.202 與 0.484。那支不及格的後來是用**同一段提示詞、換一個種子**修好的——0.484 變成 0.184。

所以：提示詞把成功率拉高，不保證結果。對一支難搞的片，**跑幾個種子、用指標挑**，不要繼續推敲字句。我們最初寫的是提示詞決定結果；那個種子實驗推翻了它。

## 該跑的順序

```
1. 樞紐幀對齊    → 這支片在片庫裡到底能不能用
2. 接縫 ÷ 動作量  → 這支片的切點會不會被看見
3. 位移         → 這是休息片還是動作片
4. jawOpen      → 嘴有沒有照規格閉著
```

沒過 1 的不能用。沒過 4 的看起來會像角色在自言自語。2 與 3 決定這支片屬於播放輪替裡的哪一層，那是 `06-playback.zh-TW.md`。


## 算出這個片庫，以及它先錯過的三種方式

上面談的都是怎麼**挑**片。這一節談怎麼**做**片，而這是花了四輪才對的部分。
每一輪都做出一個能通過當時檢查的片庫，而每一輪都有一個觀眾第一眼就看得到的缺陷。

### 第 1 輪：一個片庫裡混了兩個樞紐幀家族

反應片是按檔名挑的。其中幾支帶著一個前綴，那標記的是同一個角色的另一個沉穩層，
而那一層有它自己的樞紐幀。那些片彼此相比只差 2.7，所以看起來內部完全一致；
但拿去跟片庫其他部分比，它們離了 21（滿分 255）。

逐片自檢抓不到這個。那些片每一支都完美地起於、止於自己的樞紐幀。
檢查必須拿**一個共用基準**去比每一支，而且基準要來自片庫本身。

### 第 2 輪：海報圖不是樞紐幀

最直覺的共用基準，是播放器在第一支片畫出來之前顯示的那張海報圖。它是錯的。
拿它跟它應該代表的那些片比，某一套外觀的海報離該外觀的**每一支片**都是 4.6，
而那些片彼此在 2.9 以內。另外算的一張圖就是另外一張圖，不管它看起來多像同一格。

### 第 3 輪：整幀平均把嘴巴藏起來了

換上正確的基準之後，講話片的首幀量出來是 3.19（滿分 255），於是被判定對齊。
其實沒有。嘴巴大約只佔 432x774 畫面的百分之一，所以下巴整個換掉，
整幀平均幾乎不動：2.75 變成 3.19。而最差的 12x12 區塊變動了 13.4。

使用者第一秒就看到了，那個數字永遠不會。要回報最差區塊、用最差區塊判定，
而且不要假設臉在哪裡——真正變了的那一塊，就是值得回報的那一塊。

### 第 4 輪：真正有效的做法

三件事必須同時成立，少一件缺陷就回來。

**把音訊補到底片的長度。** 引擎會從第 0 幀開始，算 `ceil(秒數 * fps)` 幀的底片。
底片起於也止於樞紐幀，所以只有把底片跑完，算出來的片才會回到樞紐幀。
這裡的底片是 124 幀，音訊就補到一樣長。

這同時解除了來源專案當成永久限制記下來的一條規則。它的指引是對嘴來源片必須**低動作**，
因為由音訊決定長度的算圖會停在任意一幀，而動作大的來源停下來時離樞紐幀很遠——
某支撥頭髮的片量到 17.37，門檻是 9，結果做出 22 支角色的手一直沒放下來的填充片。
補長度消掉了那個任意的停點，也就消掉了避開動作的理由。
這正是量頭部動作的意義：一套引擎 0.99x，另一套 2.30x。

**前面放 0.24 秒靜音。** 否則第 0 幀帶著第一個音素的嘴型。
每一支講話片量在嘴部區域都是 5.9。

**待機片也送進同一套引擎，用靜音驅動。** 引擎連靜音時都會重生嘴部。
那張生成的中性嘴在不同次算圖之間是一致的——同一套外觀的兩支片差 1.93——
但它離原始素材的嘴 6.22。把算出來的講話片跟未經處理的反應片混在一個庫裡，
庫裡就有兩張嘴，每一個跨家族的接點下巴都會跳一下。

### 誠實地說，還剩什麼

完成的片庫裡，各支的首幀彼此在最差區塊 0.00-7.3。尾幀沒有：8.7-22.5。
底片不是原因——底片彼此在首幀是 4.1-5.5、尾幀是 5.0-7.2。
漂移是引擎在序列末端加上去的，那裡它能參考的後文最少。

加多少，是拿嘴部動作換來的：

| 表情幅度 | 接縫，最差區塊 | 備註 |
|---|---|---|
| 0.45 | 7.7 | 被判定嘴巴動得太小 |
| 0.60 | 10.2 | |
| 0.90 | 14.3 | |
| 1.20 | 17.5 | 實際採用 |

兩個修法量過之後否決。引擎自己的表情淡出讓它更糟，29.7 變成 54.1，
因為它淡向的是一張中性的臉，不是底片那張臉。
讓每支片收在最後 25 幀裡最接近基準的那一格，幾乎沒救回什麼，22.2 變成 19.9——
這正說明整段尾巴都漂了，不是某一幀壞掉。

所以這個片庫用 120 ms 的溶接播放，不是硬切。把這筆交易講白：
幅度買到嘴部動作、代價是接縫，而溶接蓋掉接縫。


### 第 5 輪：沒有聲音卻在動的嘴

輪播片不帶音訊。如果裡面的嘴會動，角色就是在對著觀眾無聲地張嘴說話，
那是這個播放器能做出最詭異的事。使用者在頁面載入幾秒內就看到了。
而這個 repo 裡的每一項檢查，都讓同一個片庫通過了。

它們會通過，是因為全部都在比對「首幀與尾幀」，而這支片是在**中段**張嘴、
到結尾又閉回去。沒有任何東西在看中間發生了什麼。

用臉部 blendshape 的 `jawOpen` 去量，九支輪播片讀到 0.140 到 0.428——
其中一支有 90% 的時間嘴是開的。兩個獨立成因，只修其中一個缺陷都還在：

  - **來源是按檔名挑的。** 一支叫 `listening` 的片量到 0.52，那是張大嘴的反應片。
    一支文件寫著「全程閉嘴」的專用底片量到 0.14，而且中段明顯把嘴唇分開。
    檔名描述的是意圖，不是內容。
  - **幅度沿用了講話片的。** 引擎連靜音都會生出嘴部動作，而表情幅度會把它放大。
    同一支底片跑靜音，幅度 0.45 時量到 0.30、幅度 1.20 時量到 0.43。
    輪播片裡沒有語音，所以它沒有理由沿用那個「為了讓說話看得清楚」而定的數字。

把每一支來源都改成量過才挑、輪播改用 0.30 而不是 1.20 之後，
同樣那九支片降到 **0.002 到 0.137**。

工具就在 repo 裡：`player/examples/check-mouth.py`。

⚠️ 門檻要對著你自己的角色在靜止狀態下校準。這裡兩張臉什麼都沒做的時候
分別讀到 0.002 和 0.14，因為其中一張的嘴唇本來就是微張的。
從別人的臉上抄一個絕對門檻過來，結果不是全部通過就是全部不過。

### 還有一個根本不在算圖層的修正

這個 demo 以前會在每個答覆之前先播一支墊詞片——「讓我想想」——
因為正式系統就是這樣做的：它有 11.9 秒的算圖要蓋，
而讓角色說一句合理的話，比轉圈圈好。

但一個全部都是預先算好的 demo 裡沒有任何東西在算，所以墊詞片什麼都沒蓋到。
它只是讓每個答覆都晚了大約四秒到，而且看起來就是「這個系統很慢」。
拿掉它之後，暴露出躲在它後面的第二段延遲：播放器只在下一次交接時才查看發話佇列，
所以在一支五秒待機片播到第一秒時提問，會先把剩下的四秒等完。

兩者現在都消失了——`speakNow()` 會就地把輪播片切斷、直接進答覆——
答覆在按下去的同一秒開始。

比這個修正更有價值的是那條通則：**墊詞片的價值，剛好等於它蓋掉的那段等待。**
對一張消費級顯卡上的 11.9 秒來說它是好答案；
在任何沒有那段等待的地方，它就只是成本。


### 還有一件修不掉的，試了三條路

其中一套外觀的片子，尾幀離自己的首幀 20-22。另外兩套是 12.6。
三套都是同一個引擎、同一個幅度、同樣的補靜音算出來的。

最可疑的是來源素材，所以同一句話在那套外觀的三種來源上各算了一次——
一支專用底片和兩支反應片，它們在算圖前自己的迴圈誤差是 4.5-5.0。
結果是 21.9、20.0、23.5。**漂移不跟著來源走。**

它跟著那張臉走。這件事值得直接寫出來、而不是留成一個開放問題，
因為有用的結論不是「我們沒修好」，而是「不要再為這套外觀多花一天挑來源片」。
120 ms 的溶接蓋得掉。如果你自己的片庫裡有一套外觀就是坐不住而其他套可以，
跨來源量一次，然後就收手。
