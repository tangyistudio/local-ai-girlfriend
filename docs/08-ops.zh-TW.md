# 實際運行：真正會發生的故障

這裡每一個故障都在正式環境上發生過。沒有一個是罕見的，而且大部分共用同一個形狀：**系統在它其實不好的時候告訴你它很好。**

---

## 最要緊的那一個：網站活著，產品死了

網頁前端與 GPU 服務在不同的機器上（見 `02-architecture.zh-TW.md`）。前端在永遠開著的託管上。模型在有顯卡的那台機器上。

所以 GPU 那台掛掉時，網站照樣回 **200**。可用性監控是綠的。首頁載得出來。一切看起來完美，直到有人真的去對話，發現角色不會說話。

這件事**一天之內發生了 3 次**——一次重開機把服務與隧道都帶走、手動救起、又掉——而**那三次都沒有任何人被通知**，因為被監控的東西沒有任何變化。

**從外部健康檢查 GPU 服務，並且對那個告警。** 打你網頁層的檢查，檢查的是你的託管商，不是你的產品。真正有意義的檢查，是那個去問模型行程一個問題、並等它回答的檢查。

## 一次只能開一個對嘴引擎

兩個對嘴模型加一個語音模型在同一張卡上：**23 GB 裡用掉 17.9 GB，GPU 97%**。語音行程還活著，而且什麼都不回應——它的 `/health` 從來沒有回答過，因為它排不到 GPU。對嘴服務於是每一個請求都以「克隆聲音服務不可用」失敗，前端無限等待，輸入框鎖死。

有兩件事讓它很難診斷：

**它是累積型的，所以看起來像隨機。** 有一次對話一開始就卡，另一次順順跑了好幾輪。沒有乾淨的重現方式，這會把你送去找一個根本不存在的競態條件。

**那個死掉的行程沒有死。** 它在跑、它在行程清單上、它佔著 port。它只是永遠不回答。**任何去看「行程在不在」而不是「有沒有回覆」的存活檢查，都會說一切正常。**

規則很簡單：**一次一個對嘴引擎。** 開另一個之前先停掉這一個。

⚠️ 細節見 `00-hardware.zh-TW.md`：一個只是**駐留**的模型幾乎不花錢。**是併發的運算在餓死其他人。** 上面那個故障需要三者同時在工作。

## 會把卡吃光的看門狗

看門狗在 `/health` 沒回應時重啟服務。合理，而且它跟一張滿的 GPU 之間有一個致命的交互作用：

1. 服務啟動不了，因為顯存不夠。
2. 但它還是開始載入了。**它現在正在佔顯存，而且還沒開 port。**
3. 看門狗看不到 `/health`，於是再開一個。
4. 回到 1。

觀察到的結果：**38 個行程**，23 GB 裡吃掉 22 GB，完全死結。每一個行程都在等其他行程佔著的記憶體。

兩個修法，缺一不可：

- **開下一個之前先確認行程在不在。** 一個正在跑的行程上 `/health` 沒回應，意思是「還在載入」，不是「死了」。
- **連續失敗要退避。** 一個沒有退避的看門狗，就是一個裝了計時器的 fork bomb。

## `/health` 回 200 不代表就緒

同一個問題的另一半。我們的對嘴服務在啟動後 **5 秒**內就以 200 回應 `/health`，接著花了將近 **4 分鐘**在 10,945 到 11,796 MiB 之間移動才穩定。

所以你真正在意的那兩個狀態——「還在載入」與「就緒」——透過一個天真的健康端點看，是彼此無法區分的，而且錯在相反的方向：

| 現實 | 天真的 `/health` 會說 |
|---|---|
| 載入中、佔著顯存、還沒開 port | 掛了（於是看門狗再 fork 一個） |
| port 開了、模型還沒載完 | 活著（於是流量進來然後逾時） |

**讓就緒真的代表就緒**：讓端點回報模型到底載完了沒，並讓看門狗去讀那個，而不是從「連線成功」去推論。

## 快取鍵：你改的東西沒有生效

**一天之內踩了 3 次。** 你改了某個東西、重跑、拿到舊行為，因為你改的那個東西不在快取鍵裡面。

抓到的有：貼圖參數、來源檔路徑、幅度。那個鍵最後必須包含 source key、來源檔路徑、來源檔的大小與 mtime、片庫指紋、聲音、語速、文字與幅度。

**任何會改變產出的東西都屬於那個鍵。** 這個失敗是無聲的——你拿到一個合法的舊檔案，不是一個錯誤——所以症狀是「我的修改沒作用」，於是你跑去錯的地方找。**如果一個參數會改變結果，它就是那個結果的身分的一部分。**

相關的一條：**檔案路徑不夠。** 同一個路徑下的兩支不同來源影片會產生同一個鍵。要把大小與 mtime 放進去，或者對內容做雜湊。

## 數行程會騙你，而且騙兩次

以下兩者都給出了很有自信的錯誤答案：

**`CommandLine -match '關鍵字'` 會把你自己的查詢算進去。** 你剛打的那個指令含有那個關鍵字，所以它出現在自己的結果裡。這產生了「有 10 個語音行程在搶卡」的計數，而實際上遠少於此，害一個下午走錯方向。

**父子行程對長得像重複的實例。** 一個透過 venv 啟動的服務會顯示兩個行程：啟動器與真正的伺服器。用名稱列出來，看起來像每樣東西都有兩份。**在你斷定有重複之前先看 `ParentProcessId`**——我們差一點回報了一個不存在的 bug。

同時比對執行檔路徑與完整命令列，並且把行程樹解出來。

## GPU 在公開網路上裸奔了 4 分鐘

驗證檢查是這樣寫的：

```python
if SERVICE_SECRET and secret != SERVICE_SECRET:
    reject()
```

**這段程式碼是對的。** 服務啟動時沒有設那個環境變數，所以 `SERVICE_SECRET` 是空字串，**整個檢查變成 no-op**，推論端點對任何完全不帶 header 的人都回 200。它透過隧道對外可達了四分鐘。

主機名是新的、從未公開過，所以實際暴露很小。但它仍然是一次真實的暴露，而教訓是結構性的：

**沒有 secret 就拒絕啟動。** 不是「警告」、不是「預設開放」——是拒絕。**缺少 secret 是一個設定錯誤**，而一個把它當成「不需要驗證」的服務，遲早會被某個趕時間的人這樣啟動。

兩個配套習慣：

- **絕不用裸的 `uvicorn` 指令啟動這些服務。** 用一支啟動腳本從你的設定檔讀出 secret 並注入，而且**找不到就結束**。
- **讓啟動腳本驗證自己的成果**：啟動之後，不帶驗證 header 打一次那個端點，並斷言它回 401。

## 開機時重啟，不是排程重啟

那個恢復工作是排在每天固定時間。一台在 01:40 重開的機器，會一直壞到那個時間到來為止。

**在開機時觸發恢復**，不是在某個鐘點。這是「掛了幾分鐘」與「掛到有人發現為止」的差別，而在一台家用機器上，01:40 沒有人在看。

## Windows 專屬的坑

這些花掉真實的時間，而且沒有一個是有趣的：

**PowerShell 5.1 用 `-Encoding utf8` 會寫入 BOM。** 這樣寫出來的設定檔被隧道守護行程整份拒絕。用 `[System.IO.File]::WriteAllText` 搭配 `UTF8Encoding($false)`。

**PowerShell 以 ANSI 讀取腳本檔案。** 一支註解裡有非 ASCII 字元的腳本，引號被吃掉、解析失敗——整份檔案，不只是那行註解。**任何要給 PowerShell 讀的檔案一律寫純 ASCII。**

**CJK 文字通過一個 code page 不是 UTF-8 的 shell 之後會壞掉。** 服務回 400，那讀起來像是服務壞了而不是請求壞了。把 payload 寫成 UTF-8 檔案再送出檔案，或在它抵達 shell 之前先跳脫成 ASCII。這一條會反覆出現；它在這個 repo 的基準測試裡也咬到我們。

**主控台輸出會死在非 ASCII 上。** 一個會印出警告符號的工具，在 cp950 主控台上會拋 `UnicodeEncodeError` 並讓整輪執行陪葬——**於是工具正好在它有話要告訴你的那一刻崩潰**。讓工具的輸出保持 ASCII，或者設 `PYTHONIOENCODING=utf-8`。

## 它們共用的形狀

上面幾乎每一個故障都是同一個 bug 換了身衣服：**一個在真相是「不好」的時候意思是「好」的訊號。**

- 後端已死的前端回 200
- 一個在跑而且永遠不回答的行程
- 在模型就緒之前就 up 的 `/health`
- 對一個改過的輸入回傳合法舊產物的快取
- 因為 secret 是空的而通過的驗證檢查
- 把執行計數的那個指令本身算進去的行程計數

當你要為這種系統加監控時，該問的問題不是「這個東西會不會在壞掉時告訴我」。而是**「這個東西到底在檢查什麼，以及有什麼可以在它照樣通過的情況下是壞的」**。
