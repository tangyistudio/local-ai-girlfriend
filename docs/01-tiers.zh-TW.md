# 各種顯卡容量的配置

8、16、24、32 GB 各該跑什麼。每一列都標明我們有沒有測過、怎麼測的——因為我們有一張卡，不是四張。

## 這些是怎麼測的

我們有一張 **24 GB 的 RTX A5000**。較小的等級是用 `bench/ballast.py` 佔住顯存、只留下目標容量，再把真正的堆疊跑在剩下的空間裡。

那模擬的是**容量**——決定模型載不載得進去、執行期會不會安靜地分流、配置器會不會開始換頁。它不模擬另一張 GPU：頻寬、核心數、快取都還是我們這張的。所以：

- **「裝得下」的宣稱是測過的**，可以套用。
- **速度的宣稱不能套用。** 這幾個等級的消費級卡，記憶體頻寬通常明顯低於工作站卡，而這個工作負載是記憶體受限的。預期會更慢。我們不打算猜慢多少——拿你那張卡的頻寬跟這張（768 GB/s）比，大致照那個比例推。
- **32 GB 沒測過。** 你沒辦法模擬出比手上更多的記憶體。那一列是算術，並且如此標示。

## 你要花掉的預算

在這台機器上暖機後量到的，出自 `docs/00-hardware.zh-TW.md`：

| 項目 | 顯存 | 備註 |
|---|---|---|
| Windows 桌面 | **1.9 - 3.4 GB** | 相隔數小時量了兩次；看你開了什麼 |
| 對嘴服務 | **約 2.4 GB** | wav2lip 這一類，256px |
| 克隆聲音 TTS | **約 5.1 GB** | 非 LLM 元件裡最貴的單一項目 |
| Qwen3 8B @ 4k ctx | **5.11 GB** | |
| Qwen3 8B @ 8k ctx | 5.74 GB | |
| Qwen3 8B @ 16k ctx | 6.89 GB | |
| Qwen3 8B @ 32k ctx | **9.54 GB** | 比 4k 多 4.4 GB —— **增加 87%** |

⚠️ **這些是上限，不是需求。** 上面每一個數字都是在有 24 GB 可用時量的，而這些元件在卡比較小的時候會縮——TTS 在 8 GB 卡上跑在約 2.7 GB 而不是 5.1 GB，速度幾乎一樣。**不要把這一欄加總然後推論小卡撐不住。** 我們就是這樣做然後錯了，見 8 GB 那一節。這張表用來看錢花在哪裡，下面測過的等級才用來決定跑什麼。

挑等級之前有兩件事要注意。

**上下文不是免費的，而預設值不夠用。** Ollama 預設 4096 token。伴侶需要人設加上對話歷史。拉到 32k 會讓模型的佔用**增加 87%**。

**貴的是克隆聲音，不是對嘴。** 大家都在預算影像模型。5.1 GB 的聲音克隆，成本是對嘴服務的兩倍多，而且它是你不夠用時第一個該搬離顯卡的東西。

## 8 GB —— 語音與對嘴在本機，LLM 遠端

**狀態：ballast 實測。跑得動，而且我們原本判斷錯了。**

```
本機：克隆聲音 TTS + 對嘴
遠端：LLM（任何託管 API）
```

用 14,836 MiB 的 ballast 把卡限制在 8,192 MiB 之後量到。下面每一列都**記錄在** `bench/results.json` 裡；ballast 的大小寫在基線的標籤上，所以你可以自己還原出卡內數字。

| | 數值 | |
|---|---|---|
| 桌面，上 ballast 之前 | 2,263 - 2,660 MiB | recorded |
| 兩個服務都載入並實際工作，卡內 | **8,192 MiB 之中的 7,052 - 7,615** | recorded |
| 跑完探測套件之後 | 6,887 MiB | recorded |
| TTS，短句 | 2.80 秒（24 GB：2.38 秒）| recorded |
| TTS，長句 | 12.24 秒（24 GB：12.36 秒）| recorded |
| 對嘴，短 | 0.88 秒（24 GB：0.82 秒）| recorded |
| 對嘴，長 | 3.01 秒（24 GB：3.12 秒）| recorded |

**長句與對嘴完全沒有變慢。** 短句 TTS 在這一輪慢 18%。

⚠️ 同一格先前的一輪，短句量到 3.01 秒——是慢 26% 而不是 18%。**兩輪都是真的，而兩次作業之間的差距大於被量測的效應本身**，那件事值得在你依單一數字做規劃之前先知道。兩輪之間穩定不變的是：**這一格跑得動，而且變慢的不是那些貴的操作。**

### 我們預測這一格會失敗，而且把預測發出去了

這一頁的第一版寫著 8 GB 不可能：桌面吃約 3.2 GB、TTS 是 5.1 GB，這樣就已經超過了。然後我們跑了一次。

那個算術是錯的，因為 **TTS 不是 5.1 GB**。它在有 24 GB 可用時是 5.1 GB，在沒有的時候大約 2.7 GB，做一樣的事、速度幾乎一樣。在大卡上量到的元件大小，是使用量的上限，不是需求量。

我們刻意把錯的預測留在文件裡。它是我們手上最清楚的示範，說明為什麼不該用別人的數字去推算一台機器的規格——包括我們的數字。

### 什麼裝不下

8B 模型即使被壓縮也要約 5.35 GB。剩下 694 MiB 是塞不下的，所以在這一格，語言模型要走 API。

⚠️ 那代表你的對話會離開這台機器。對很多人來說，那正是自架的全部理由，而這一格把它放棄了。如果本機推論才是重點，8 GB 不是你的等級。

### 這一格暴露出的一個設計需求

我們量的這個參考伺服器**沒有本機 TTS 就跑不了對嘴**。`_render` 把語音寫進暫存目錄，每一次快取未命中都呼叫 TTS 服務；**沒有任何端點接收你已經有的音訊**。

所以「TTS 在遠端」不是一個你可以選的設定——它需要一個能連同文字一起接收音檔或 URL 的 API。任何打算支援這一格的實作都必須提供這個端點。我們的會。

## 16 GB —— 全部本機，但很緊

**狀態：ballast 實測。跑得動，但有一個要緊的但書。**

我們模擬了一張 16 GB 的卡，跑完整堆疊：克隆聲音 TTS、對嘴，以及 32k 上下文的 Qwen3 8B。

| 量測 | 24 GB | 模擬 16 GB |
|---|---|---|
| Token 生成 | 86.3 tok/s | **86.5 tok/s** |
| 27,523 token 的提示 | 12.0 秒 | **16.0 秒**（+33%）|
| 完整 27.5k 上下文有處理完嗎？ | 有 | **有** |

生成速度一模一樣。很長的上下文在提示處理上慢三分之一。兩者都可用。

### 但書：結果取決於你什麼時候量

我們那次 16 GB 測試的地板是桌面＋TTS＋對嘴 8,489 MiB，而完整堆疊就跑在裡面。同樣這三者後來在不受限、且持續使用之後的讀數更高——**recorded 是 9,409 到 9,546 MiB**，另有一個在 ballast 之下取得的 **session** 讀數 9,920 MiB。

⚠️ **我們先前拿 9,920 去算，結論是這一格在負載下會超過天花板。我們撤回那個結論**，理由有二：

1. 它用了一個 **session** 數字，而 `results.json` 裡有更低的 recorded 數字，**而結論在那個範圍內會翻面**：9,546 ＋ 6,924 = 16,470（超過 86 MiB），9,409 ＋ 6,924 = 16,333（**沒超過**）。
2. 它正是這一頁前面兩節明令禁止的那種加總——拿大卡的元件數字去預測小卡，而那正是我們把 8 GB 判錯的方式。

我們能說的是我們量到的：**16 GB 這個配置從冷啟動跑起來了，而且是全速。** 它撐不撐得過好幾小時的持續使用，我們沒有測。如果你要的是餘裕而不是擲骰子，16k 上下文留得下空間；那是一個建議，不是一次量測。

```
16 GB 已測：    TTS 本機 + 對嘴本機 + 8B @ 32k ctx —— 從冷啟動全速跑起來
16 GB 建議：    同上但 16k ctx，留一點我們沒驗證過是否必要、但代價很小的餘裕
```

## 24 GB —— 舒服，也是我們實際在跑的

**狀態：直接實測。這個 repo 裡其他所有東西都是在這台機器上量的。**

整套堆疊在這裡跑起來而且還有餘裕，那正是這一格的意義：**它是第一個你不需要管理預算的等級。**

⚠️ 我們刻意**不**在這裡印出元件欄位的加總。早期版本印了，而它跟這一頁前面兩節自己的警告互相矛盾——正是那套推理讓我們宣告 8 GB 不可能。**元件會縮小以求適配；一堆上限的加總不是一個需求。** 量到的事實是：它跑起來了。

**27B 塞得下，但你要用速度去換。** 在邊緣服務運作中的情況下載入 Qwen3.8 27B，卡被推到 23,028 MiB 中的 22,528 MiB —— 97.8%。它跑得起來，而且我們量了：

| 模型 | 吞吐量 | 冷載入 |
|---|---|---|
| Qwen3 8B | **86.3 tok/s** | 15.6 秒 |
| Qwen3.8 27B | **19.9 tok/s** | 16.5 秒（僅載入） |

**每個 token 慢 4.3 倍。** 對一個要在對話時間內回應的伴侶來說，那是「上一句還沒讀完下一句就到了」跟「你要等」的差別。除非 27B 在你這個特定任務上明顯比較好，否則在這張卡上 8B 是比較好的產品決定。

## 32 GB —— 只有算術

**狀態：沒測過。我們沒有這個硬體。**

從上面的數字反推，32 GB 應該裝得下完整的本機堆疊再加上一個大得多的模型，或者 8B 配上長得多的上下文。我們不打算講得更具體，因為那會是編的。

有一件我們真的量到的事可以說：在這套堆疊上，我們撞到的是**容量的牆，不是算力的牆**。一顆 27B 模型把卡填到 97.8%。如果你在挑硬體，先買記憶體再買算力。

## 比等級更重要的那條規則

我們把探測集跑了三輪：單獨、27B 駐留但閒置、27B 正在生成。

| 探測 | 單獨 | 駐留閒置 | 生成中 |
|---|---|---|---|
| 對嘴，短 | 0.82 秒 | 0.89 秒 | **1.11 秒** |
| 對嘴，長 | 3.12 秒 | 2.94 秒 | **5.00 秒** |

一個駐留但閒置的模型，即使它把卡填滿，成本量不出來。一個正在生成的模型，**短片段讓你付 1.35 倍、長片段 1.6 倍**。

**一起載入撐得住，一起運算不免費。** 如果你的管線是循序的——使用者說話、LLM 回答、然後 TTS、然後對嘴——你主要付的是駐留成本，上面這些等級成立。如果你為了壓延遲而讓各階段重疊，那個重疊要計價。

## 在 Windows 上怎麼讀自己的工具

在你相信任何容量數字之前，有兩個失效模式要知道：

**`ollama ps` 報的是意圖，不是顯存。** 在邊緣服務運作中，它對 27B 回報「17 GB，100% GPU」，而實測 delta 是 11.5 GB。在 ballast 之下跑 32k，它回報「10.0 GB，100% GPU」，而 delta 是 6.9 GB。**它一次都沒說過自己分流了。**

**WDDM 用超額配置取代失敗。** 在 Windows 上，驅動會把超出實體顯存的配置溢出到系統記憶體。沒有 OOM、沒有錯誤、沒有 log ——只有一台變慢的機器。這跟大多數指南假設的 Linux 行為相反。

這兩件事加起來的意思是：**在 Windows 上，你無法從工具判斷一個配置裝不裝得下。** 唯一誠實的訊號是吞吐量——空卡跑一次 `bench/tok_rate.py`，再在 `bench/ballast.py` 之下跑一次。速率沒掉就是裝得下。
